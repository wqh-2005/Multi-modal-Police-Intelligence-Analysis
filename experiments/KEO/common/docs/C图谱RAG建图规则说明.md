# C 图谱 RAG 建图规则说明

本文依据同目录《数据结构与交付说明.md》的格式1.1，说明如何使用A清洗后交付的数据建图。建图直接采用已有实体类型、人物角色和关系，不再调用大模型重新判断人物真假、识别冒充身份或进行全量共指消解。本文规定设计方案，不表示代码已经实现。

## 一 核心规则

**人员看role，身份和机构看type，联系直接用relation。**

- `type=人员`、`role=疑似诈骗者`：在本实验图谱中归类并展示为“诈骗犯”，保留原始role字段。
- `type=人员`、`role=受害人`：归类为“受害人”。
- 人员使用案件ID和原实体ID确定节点，不跨案合并，也不因角色相同合并不同实体ID。
- `type=身份角色`的“客服”等是身份概念，可以跨案共享同一节点，不是具体人物。
- 明确相同的机构、应用产品等按清洗后的规范名称共享节点。
- `relation=冒充`直接采用；没有冒充关系就不增加，大模型已识别的结果无需在建图阶段重新判定。

这里的“诈骗犯”是按交付role生成的图谱分类和展示名称；数据中原有的`role=疑似诈骗者`、证据和审核状态仍原样保存，不将建图转换记录成人工核验。

## 二 使用A交付的数据

| 文件 | 使用方法 |
| --- | --- |
| `案例数据.json` | 按`id`读取原文和类别，用于关联与证据追溯 |
| `三元组数据.jsonl` | 读取head、tail、relation及事实状态、证据等字段 |
| `划分名单.json` | 只使用`build_ids`中的案例建图和建立检索索引 |

关联方式为`案例id = 三元组source_id`。`eval_ids`中的案例和三元组不进入知识库。没有三元组的建库案例记录在报告中，不私自改变共同划分。

A已完成约定的清洗，C不再重复进行全量语义审核。建图入口只检查必填字段、ID对应、重复ID及建库范围等结构问题。

## 三 如何确定人员节点

### 3.1 按案件和原实体ID建节点

内部唯一键使用`(source_id, entity.id)`，存储时采用元组或无歧义编码。原实体ID已包含案件前缀时，也可以沿用该ID，同时校验其来源。

| type | role | 图谱分类 | 节点范围 |
| --- | --- | --- | --- |
| 人员 | 疑似诈骗者 | 诈骗犯 | 案件内，保留原实体ID |
| 人员 | 受害人 | 受害人 | 案件内，保留原实体ID |
| 人员 | 其他值或null | 保留原值或普通人员 | 案件内，保留原实体ID |

例如第二张图：

```text
case_011844_E005：诈骗犯，原称呼“对方”
case_011844_E001：受害人，原称呼“报警人”

case_011844_E005 ─要求转账→ case_011844_E001
事实状态：被要求执行
```

不需要再判断“对方”是否冒充某个身份；这条三元组没有冒充关系，就仅建立要求转账关系。

### 3.2 UNKNOWN不影响建图

若`name=UNKNOWN`或“未知”，仍按原实体ID、type和role建图：

```text
id：case_001572_E007
原名称：UNKNOWN
type：人员
原role：疑似诈骗者
图谱分类：诈骗犯
展示名称：诈骗犯（姓名未知）
```

同样，name为“客服”“贷款业务员”“对方”时，只要role为疑似诈骗者，就归为诈骗犯。原name保留为称呼，不影响人员分类，也不因此把人物映射到共享身份节点。

不同案件的诈骗犯保留不同ID；同案不同实体ID也保留不同节点。同一原实体ID反复参与关系时复用已有节点，不额外拆分，也不额外进行人物合并。

## 四 如何确定共享节点

### 4.1 按实体类型和清洗后的名称共享

| 实体内容 | 建图规则 | 示例 |
| --- | --- | --- |
| 身份角色 | 同一规范身份名称共享 | 客服、京东客服、军人分别建立身份概念 |
| 机构 | 同一明确机构名称共享 | 同一银行或单位概念 |
| 应用程序 | 同一明确应用产品共享 | 微信、QQ、云视讯 |
| 平台 | 同一明确平台共享 | 清洗确认的具体平台 |
| 人员 | 不跨案共享 | 诈骗犯、受害人、客服人员 |
| 账户和具体账号 | 默认案件内保存 | 银行卡、微信账号 |
| 金额、时间、具体地点和文件材料 | 默认案件内保存 | 某笔金额、“家中”、转账截图 |

共享概念的键使用`(concept, 规范类型, 规范名称)`，人员的键使用`(source_id, entity.id)`。因此，即便人员和身份都叫“客服”，也不会合并在一起。

采用A已清洗的名称；若A另外提供确认的别名映射则直接使用。不新增语义相似度自动合并流程。尚未规范的名称保留并记录，后续统一维护映射。

“某APP”“未知机构”等缺失或泛指名称保留局部节点；相同账号尾号不自动合并。微信产品与微信账号不合并，微信与微信微粒贷不当作同义词。

### 4.2 第一张图如何建图

第一张图的head和tail虽然都叫“客服”，但类型不同：

```text
head：case_012615_E003，name=客服，type=人员，role=疑似诈骗者
    → 案件内诈骗犯节点

tail：case_012615_E004，name=客服，type=身份角色，role=null
    → 共享身份节点“客服”

案件内诈骗犯 ─冒充→ 客服身份
```

其他案例也有`type=身份角色、name=客服`时，映射到同一个“客服身份”节点；其诈骗犯节点仍按各自案件ID保存。

```text
case_012615_E003 ─冒充→ 客服身份 ←冒充─ 其他案件诈骗犯
```

如果冒充对象的type是机构，则连接相应机构节点；不需要再生成一轮身份判定。清洗后的“客服”“京东客服”等不同细分名称不无条件合成一个概念。

### 4.3 保留原实体到图谱节点的映射

每个原实体保存映射：

```text
(source_id, original_entity_id) → graph_node_id
```

共享概念记录所有来源实体ID和原名称，便于追溯。人员角色映射也保存原role与图谱分类，不覆盖原始字段。相同局部ID出现矛盾字段时报告冲突，不用最后一条静默覆盖。

## 五 如何建立联系

### 5.1 直接映射三元组

每条三元组按以下步骤处理：

1. 根据head的type和role确定节点分类，取得头节点ID。
2. 根据tail的type和role确定节点分类，取得尾节点ID。
3. 直接以relation建立有向关系。
4. 保存source_id、triple_id、factuality、evidence、confidence、status。

人员role用于分类，不用于凭空增加关系。已有“冒充”“要求转账”“下载”等关系直接采用，不重新推断。

例如：

```text
诈骗犯A ─冒充→ 客服身份
诈骗犯A ─要求下载→ 云视讯
受害人A ─下载→ 云视讯
```

这三条可以共存。“要求下载”与“实际下载”分别保留，不能相互替代。

### 5.2 保留多条关系与证据

- 原始事实唯一键为`(source_id, triple_id)`。
- 同一对节点可以存在多种关系，不让后写关系覆盖前写关系。
- 不仅凭“头、关系、尾”相同就删除记录，不同证据可能对应多次行为。
- 每条事实保存原文证据的unit_id和text，不用节点展示名称替换证据文字。
- 同一数值不代表同一次付款；不把缺失金额当成0，也不凭共现强行拼接付款对象、时间和金额。
- confidence和status直接保留，不因导入图谱就改为人工审核完成。

需要计算结构权重时，可从事实记录派生支持次数或不同支持案例数，并固定统计口径。不能为了提高权重把不同案件人物合并。role相同的人员行为统计可以另外分组计算。

## 六 字段映射示例

以下为展示如何存储人员节点的内部结构示例，不是新的A交付要求：

```json
{
  "graph_node_id": "case_001572_E007",
  "source_id": "case_001572",
  "original_entity_id": "case_001572_E007",
  "original_name": "贷款业务员",
  "type": "人员",
  "role": "疑似诈骗者",
  "graph_category": "诈骗犯",
  "display_name": "诈骗犯（贷款业务员）"
}
```

展示名称可以简化，但检索结果应同时标明案例，避免不同人员显示相同造成误解。对UNKNOWN人员可以使用“诈骗犯（姓名未知）”或“受害人（姓名未知）”。

## 七 建图到检索的执行顺序

```text
A交付清洗后的数据包
    ↓
按build_ids筛选案例和三元组
    ↓
人员按案件内ID建节点，role映射为图谱分类
    ↓
身份、机构、APP等按类型和规范名称建立共享节点
    ↓
直接导入原有关系、事实状态、证据和来源
    ↓
建立节点检索索引
    ↓
根据问题检索种子节点、扩展邻居、最大生成树筛选
    ↓
恢复原有关系方向，组织带来源的上下文
    ↓
向公共回答模块输出格式1.3
```

人物节点可用原名称、type、role和图谱分类构建检索描述，UNKNOWN人员仍可通过“诈骗犯”“受害人”等角色检索。身份和APP节点使用规范名称检索。相似检索命中不同人物，不意味着把人物节点合并。

## 八 与公共接口一致的交付要求

C输出《数据结构与交付说明.md》格式1.3：`question_id`、`method=graph_rag`、`status`、`context`、`evidence`、`elapsed_ms`、`error`。

- evidence中保留evidence_id、source_id、原文text，可补充triple_ids。
- 所有检索证据必须来自build_ids中的案例。
- 上下文可以使用图谱分类“诈骗犯”，证据text保持原文；原始role仍可追溯。
- 共享身份节点形成的跨案路径，不写成所有人物属于同一团伙或同一案件。
- 保留“冒充”和“要求执行”等关系原义，不在文字重建时丢掉它们。
- 无结果为empty，执行失败为error，不混淆两种状态。
- 类别是否进入上下文与B统一约定，不自动加入D的真实类别或评分资料。

第一版以复用既有role、type和relation为准，不增加真假客服识别、全量共指消解或重新抽取流程。建图报告记录节点数、关系数、共享概念数和结构异常即可。
