# KEO 系统验证报告

**对象：** 诈骗案例研判系统（KEO 实验）
**验证日期：** 2026-11-17
**验证范围：** 数据交付、文本检索、图谱检索、评测四个子系统的端到端可用性

---

## 一、系统概述

本系统回答一个问题：**给定一条诈骗案情，判定它属于 11 类中的哪一类、依据是哪几条、该怎么处置，并评估这套判定准不准。**

### 1.1 四个子系统与职责

| 子系统 | 职责 | 对外产物 |
|---|---|---|
| **A 数据** | 数据对齐、去重、60/40 划分、名称清洗、交付包导出 | 格式 1.1 交付包（案例 / 三元组 / 划分名单 / 别名映射） |
| **B 文本检索** | 案情分句、向量建库、文本检索、**公共回答模块** | 格式 1.3（检索）/ 1.4（回答） |
| **C 图谱检索** | 三元组建图、节点向量、子图检索、上下文重建 | 格式 1.3（含 `triple_ids`） |
| **D 评测** | 出题、金标、五维评分、分类指标、汇总报告 | 格式 1.2 / 1.5 / 1.6 + 报告 |

### 1.2 三种判定方法

系统对比三种方法，共用同一提示词、同一模型、同一参数，只改检索来源：

| 方法 | 检索来源 | 依据可溯源 |
|---|---|---|
| `direct` | 无，直接判 | ❌ |
| `text_rag` | 相似案情片段（文本向量库） | ✅ 案例编号 |
| `graph_rag` | 知识图谱实体与关系 | ✅ 案例编号 + 三元组编号 |

### 1.3 数据流向

```
A 交付包
  ↓  core/ingest.py（唯一入口，登记 SHA256）
data/v1.1/
  ├─→ B: build_data → clause.build_chunks → build_index → retrieve ─┐
  ├─→ C: grapy_builder → node_index → GraphRAG.retrieve ────────────┤
  └─→ D: 题库 + 金标                                               │
                                                                    ↓
                                            answerer.answer_one（汇合点）
                                                                    ↓
                                                        格式 1.4 → D 评分
                                                                    ↓
                                              evaluations(1.6) → metrics → report
```

**关键设计**：B 与 C 是两条并列检索链，产出**同一个格式 1.3**，汇合到同一个 `answer_one`。因此 1.3 是全系统最关键的契约。

## 二、验证方法

分四层，逐层加压：

| 层级 | 手段 | 目的 |
|---|---|---|
| L1 静态 | 模块导入、语法编译、离线自测 | 代码完整性 |
| L2 数据 | 全量导入 + 三方条数一致性校验 | 数据完整性与划分正确性 |
| L3 单链 | 每条链独立跑真实数据 | 各子系统可用 |
| L4 端到端 | 契约测试 + 小规模沙盒 + 评测闭环 | 跨子系统贯通 |

其中 L4 采用**规模受限验证**：从 49,289 篇建库案例随机抽 1,000 篇，在独立数据库里建小图 + 小索引，使图谱链在分钟级达到 `ready`，从而真实验证 C 的检索，而不必等待 6 小时全量向量化。

## 六、系统能力边界

### 已验证可用

1. 数据交付与导入的一致性校验（三层：源 SHA256 / 自身 SHA256 / 跨文件条数）
2. 文本检索链全流程
3. 图谱建图全流程（全量规模）
4. 图谱检索链（1,000 例规模，真实返回）
5. 1.3 → 1.4 跨子系统契约
6. 五维评分、分类指标、汇总报告
7. 系统级体检工具（7 段 smoke test）、进度观测、断点续跑守护

### 尚未验证 / 不可用

| 项 | 原因 |
|---|---|
| 全量图谱检索 | 节点向量 23.1%，需再约 5–6 小时 |
| `run_b` 跑通 `graph_rag` 的完整答案 | 只在沙盒验证了 `GraphRAG.retrieve` 单点，未走完 `run_b` 全流程 |
| 三方法同题对比 | 缺 `graph_rag` 答案 |
| A 的脚本执行 | 缺原始数据 |
| D 的 `run_pairwise` / `generate_questions` | 仍为硬编码本地脚本，未接入配置 |

### 已知工程质量问题（已修复）

| 问题 | 修复 |
|---|---|
| 共享 embedding 组件无重试、走系统代理 → 长任务整段失败 | 加代理隔离 + 400 拆分 + 退避重试 + 空/超长兜底 |
| 检索失败仍生成答案，被计为成功 | 按格式 1.4 §8 阻止生成，外层记 `status=error` |
| `run_b` 少量结果覆盖大量已有结果 | 加防覆盖护栏（变少即拒绝，需 `--force`） |
| `run_b` 不支持 `graph_rag` | 已接入，共用单个事件循环 |

## 八、复现方式

```powershell
# 系统体检（7 段，40 秒）
.\.venv\Scripts\python.exe experiments\KEO\tools\smoke_test.py

# 只看进度
.\.venv\Scripts\python.exe experiments\KEO\tools\progress_line.py

# 文本链
python -m experiments.KEO.core.ingest
python -m experiments.KEO.core.text_rag.build_index
python -m experiments.KEO.core.text_rag.run_b --questions <题库> --methods direct,text_rag

# 图谱链（全量）
python -m experiments.KEO.core.graph_rag.grapy_builder
python -m experiments.KEO.core.graph_rag.node_index --resume

# 评测链
python -m experiments.KEO.core.evaluation.run_eval --workers 3
python -m experiments.KEO.core.evaluation.metrics
python -m experiments.KEO.core.evaluation.report
```

沙盒复现：设 `KEO_NEO4J_DATABASE=keosmoke`、`KEO_CHROMA_PERSIST_DIR=…/node_vectors_smoke`、`KEO_CHROMA_COLLECTION=keo_smoke_nodes`、`KEO_SPLIT_PATH=…/划分名单_smoke.json` 后重复图谱链三步。

## 九、结论

1. **系统架构成立**：四个子系统通过 6 种文件格式解耦，两个跨角色函数（`answer_one`、`GraphRAG.retrieve`）承担全部耦合，替换任一内部实现不影响上下游。
2. **三条检索路径全部实现且有真实数据跑通**（graph_rag 在 1,000 例规模验证）。
3. **评测闭环完整**：从答题到五维评分、分类指标、汇总报告全程可执行。
4. **当前唯一系统性阻塞是规模**：46 万实体向量化需 5–6 小时，属算力/时间成本，不是代码缺陷。
5. **两处工程欠账**：A 脚本未在本机执行验证、D 的两个辅助脚本未改造。
