# KEO 总接口设计文档

> 本文只定义 A、B、C、D 之间交接的数据结构。批量交付采用文件，单条记录也可直接作为模块调用参数；不要求开发 HTTP 接口。保留现有案例和三元组字段。

## 一 数据流与接口总览

```text
A ── 案例、三元组、划分名单 ──→ B、C、D
D ── 问题 ──→ B、C及直接回答流程
B ── 文本检索结果 ──→ 公共回答模块
C ── 图谱检索结果 ──→ 公共回答模块
公共回答模块 ── 三种方法的回答及证据 ──→ D
D ── 评分及方法比较结果 ──→ 团队汇总
```

| 格式 | 上游 → 下游 | 内容 |
| --- | --- | --- |
| 1.1 | A → B、C、D | 案例、三元组、划分名单 |
| 1.2 | D → B、C及直接回答流程 | 问题 |
| 1.3 | B、C → 公共回答模块 | 检索上下文与来源证据 |
| 1.4 | 公共回答模块 → D | 三种方法的最终回答、检索上下文与证据 |
| 1.5 | D内部使用 | 题目来源与真实类别，不进入回答流程 |
| 1.6 | D → 团队 | 逐条评分与成对比较结果 |

B牵头维护公共回答模块，B、C共用同一套调用逻辑。B负责文本RAG与直接回答，C负责图谱RAG；D统一接收格式1.4，不需要分别适配两套结构。

## 二 A的数据输出 B C D的输入 格式1.1

交付文件：`案例数据.json`、`三元组数据.jsonl`、`划分名单.json`。A提供同一个数据包，不分别制作B版和C版。

### 2.1 案例数据

```json
[
  {
    "id": "case_000001",
    "案情描述": "对方称刷单可以赚钱，要求受害人下载某应用。",
    "案件类别": "刷单返利类"
  }
]
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 现有案例编号，唯一且不重新编号 |
| `案情描述` | string | 是 | 完整案例原文，不附加类别或评分说明 |
| `案件类别` | string | 是 | 使用统一类别集合的原有类别 |

### 2.2 三元组数据

JSONL每行一条，沿用现有结构：

```json
{
  "triple_id": "case_000001_T001",
  "source_id": "case_000001",
  "source_type": "案例",
  "fraud_category": "刷单返利类",
  "head": {"id": "case_000001_E001", "name": "对方", "type": "人员", "role": "疑似诈骗者"},
  "relation": "要求下载",
  "tail": {"id": "case_000001_E002", "name": "某应用", "type": "应用程序", "role": null},
  "factuality": "被要求执行",
  "evidence": [
    {"unit_id": "case_000001_clause_001", "text": "对方称刷单可以赚钱，要求受害人下载某应用。"}
  ],
  "confidence": 0.95,
  "status": "待人工审核"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `triple_id` | string | 是 | 原有三元组编号，与`source_id`组合唯一 |
| `source_id` | string | 是 | 对应案例数据的`id` |
| `source_type` | string | 是 | 本项目使用`案例` |
| `fraud_category` | string | 是 | 与对应案例的`案件类别`一致 |
| `head`、`tail` | Entity | 是 | 头实体和尾实体 |
| `relation` | string | 是 | 现有关系名称，保留方向 |
| `factuality` | string | 是 | 保留“明确发生”“被要求执行”等事实状态 |
| `evidence` | EvidenceUnit[] | 是 | 支持关系的原文证据 |
| `confidence` | number或null | 否 | 保留已有抽取置信度，不等于人工确认正确率 |
| `status` | string或null | 否 | 保留已有审核状态 |

| 子结构 | 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| Entity | `id` | string | 是 | 原有实体ID，按所属案例理解 |
| Entity | `name` | string | 是 | 原有实体名称 |
| Entity | `type` | string | 是 | 实体类型 |
| Entity | `role` | string或null | 否 | 人物角色，保留已有值 |
| EvidenceUnit | `unit_id` | string | 是 | 原文语句单元编号 |
| EvidenceUnit | `text` | string | 是 | 原文证据文字 |

关联规则：案例`id = 三元组source_id`。不同案例中同名的“对方”“受害人”不因此视为同一个人物。允许保留现有附加字段，无需转换为ARETO标注格式。

### 2.3 划分名单

```json
{
  "build_ids": ["case_000001", "case_000002"],
  "eval_ids": ["case_000003", "case_000004"]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `build_ids` | string[] | 是 | 约60%的建库案例编号，B、C共用 |
| `eval_ids` | string[] | 是 | 约40%的统计分析、出题和评估资料编号，D使用 |

两份名单不重叠，ID必须存在于案例数据，重复案例不能跨侧。B按建库名单读取原文，C读取同批三元组及原文。没有三元组的案例须在交付说明中记录，不得由B、C各自静默排除。

## 三 D的问题输出 B C及直接回答流程的输入 格式1.2

文件：`questions.jsonl`，每行一道题。

```json
{
  "question_id": "q001",
  "question_type": "case_judgment",
  "question": "对方称刷单可以赚钱，并要求下载应用充值。请判断诈骗类型、指出证据并提出应对措施。"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question_id` | string | 是 | 问题唯一编号 |
| `question_type` | string | 是 | `global_analysis`全局分析；`case_judgment`案例研判 |
| `question` | string | 是 | 完整问题；案例题同时包含待分析正文 |

三种方法接收完全相同的问题。该格式不包含真实类别、参考措施、出题来源ID或统计摘要，也不设置区分测试和正式阶段的字段。

## 四 B C的检索输出 公共回答模块的输入 格式1.3

两种RAG共用此结构：

```json
{
  "question_id": "q001",
  "method": "graph_rag",
  "status": "ok",
  "context": "[E001] 案例case_000001中，对方要求受害人下载某应用。",
  "evidence": [
    {
      "evidence_id": "E001",
      "source_id": "case_000001",
      "text": "对方称刷单可以赚钱，要求受害人下载某应用。"
    }
  ],
  "elapsed_ms": 120,
  "error": null
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question_id` | string | 是 | 回显输入的问题编号 |
| `method` | string | 是 | `text_rag`或`graph_rag` |
| `status` | string | 是 | `ok`成功；`empty`无结果；`error`失败 |
| `context` | string | 是 | 实际交给回答模型的上下文 |
| `evidence` | RetrievedEvidence[] | 是 | 上下文对应的原文证据列表 |
| `elapsed_ms` | number | 是 | 检索耗时，单位毫秒 |
| `error` | Error或null | 是 | 成功或无结果为`null`，失败填写错误对象 |

### RetrievedEvidence字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `evidence_id` | string | 是 | 本条检索结果内唯一，供上下文和回答引用 |
| `source_id` | string | 是 | 证据所属案例，必须在`build_ids`中 |
| `text` | string | 是 | 实际使用的原文证据，不能用图谱推断冒充 |
| `triple_ids` | string[] | 否 | C可补充关联的三元组编号 |
| `chunk_id` | string | 否 | B可补充关联的文本块编号 |

图路径、种子节点和相似度等仅作为各自附加信息，不要求D读取。直接回答不调用检索器，回答模块使用空上下文和空证据。

## 五 三种方法的回答输出 D的输入 格式1.4

文件：`answers.jsonl`。B、C通过公共回答模块产生同一格式；将实际使用的上下文和证据一并交给D，避免另查多份检索文件。

```json
{
  "run_id": "run_001",
  "question_id": "q001",
  "method": "graph_rag",
  "model_id": "实际使用的回答模型标识",
  "status": "ok",
  "answer_text": "这里保存完整回答，包括判定、证据说明与措施。",
  "predicted_category": "刷单返利类",
  "cited_evidence_ids": ["E001"],
  "parse_status": "ok",
  "retrieval": {
    "status": "ok",
    "context": "[E001] 案例case_000001中，对方要求受害人下载某应用。",
    "evidence": [
      {
        "evidence_id": "E001",
        "source_id": "case_000001",
        "text": "对方称刷单可以赚钱，要求受害人下载某应用。"
      }
    ],
    "elapsed_ms": 120,
    "error": null
  },
  "generation_elapsed_ms": 1000,
  "error": null
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `run_id` | string | 是 | 一次执行的编号，用于区分重跑，不代表数据阶段 |
| `question_id` | string | 是 | 对应D的问题 |
| `method` | string | 是 | `direct`、`text_rag`、`graph_rag` |
| `model_id` | string | 是 | 实际回答模型，三种方法按同一模型比较 |
| `status` | string | 是 | `ok`回答生成成功；`error`生成失败 |
| `answer_text` | string | 是 | 完整模型回答，解析失败也保留 |
| `predicted_category` | string或null | 是 | 案例题预测类别；全局题、无法解析或类别无效时为`null` |
| `cited_evidence_ids` | string[] | 是 | 对应本条`retrieval.evidence`的引用编号；无引用为`[]` |
| `parse_status` | string | 是 | `ok`解析成功；`error`解析失败；`not_applicable`不需要解析 |
| `retrieval` | object | 是 | 格式1.3的`status/context/evidence/elapsed_ms/error`五个字段 |
| `generation_elapsed_ms` | number | 是 | 回答模型调用耗时，单位毫秒 |
| `error` | Error或null | 是 | 回答生成错误，正常为`null`；检索错误保留在`retrieval.error` |

D通过`run_id + question_id + method + model_id`唯一定位回答。案例正文自身也可以作为判定依据，不强制所有依据均来自检索证据。

直接回答使用同一结构，但`retrieval.status=not_applicable`，上下文为空字符串、证据为空列表、检索耗时为0、检索错误为`null`。

## 六 D内部的题目评价资料 格式1.5

仅D读取，不传给B、C或公共回答模块。建议文件：`question_metadata.jsonl`。

```json
{
  "question_id": "q001",
  "origin_source_ids": ["case_000003"],
  "gold_category": "刷单返利类"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question_id` | string | 是 | 与问题文件对应 |
| `origin_source_ids` | string[] | 是 | 出题依据的案例编号；综合题可对应多篇，必要时另保存出题依据 |
| `gold_category` | string或null | 是 | 案例题已有真实类别；全局题为`null` |

不要求提前编写完整措施答案，也不强制建立`references.jsonl`。D可对照来源案例，在生成回答后组织人工审核；如后续补充参考措施，作为D内部可选信息保存。

## 七 D的评价输出 格式1.6

### 7.1 逐条评分

文件：`evaluations.jsonl`。

```json
{
  "run_id": "run_001",
  "question_id": "q001",
  "method": "graph_rag",
  "model_id": "实际使用的回答模型标识",
  "evaluator_id": "人工审核者或评判模型标识",
  "scores": {
    "类型判定": 5,
    "证据指向": 4,
    "措施正确性": 4,
    "可执行性": 4,
    "完整性": 3
  },
  "reason": "评分理由",
  "status": "ok",
  "error": null
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `run_id/question_id/method/model_id` | string | 是 | 四个字段共同对应具体回答 |
| `evaluator_id` | string | 是 | 实际人工审核者或评判模型 |
| `scores` | object或null | 是 | 各维度1—5分，评分失败为`null` |
| `reason` | string | 是 | 评分依据或错误说明 |
| `status` | string | 是 | `ok`或`error` |
| `error` | Error或null | 是 | 评分失败时记录错误 |

| 题型 | `scores`中使用的维度 |
| --- | --- |
| 全局分析题 | 综合质量、模式识别、决策价值、全局视角、主题识别 |
| 案例研判题 | 类型判定、证据指向、措施正确性、可执行性、完整性 |

类型识别的Accuracy、Macro-F1等由`predicted_category`和`gold_category`直接计算，与上述维度评分分别报告。

### 7.2 成对比较

如需直接比较两种方法的回答，保存以下记录；未采用成对评价时不强制生成。

```json
{
  "run_id": "run_001",
  "question_id": "q001",
  "model_id": "实际使用的回答模型标识",
  "evaluator_id": "人工审核者或评判模型标识",
  "method_a": "text_rag",
  "method_b": "graph_rag",
  "winner": "b",
  "reason": "方法b的证据更充分",
  "status": "ok",
  "error": null
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `run_id/question_id/model_id` | string | 是 | 限定同一次运行、同一问题和同一回答模型 |
| `evaluator_id` | string | 是 | 本次评判者 |
| `method_a/method_b` | string | 是 | 两个不同方法，取值同格式1.4 |
| `winner` | string或null | 是 | `a`、`b`、`tie`；评价失败为`null` |
| `reason` | string | 是 | 比较理由 |
| `status` | string | 是 | `ok`或`error` |
| `error` | Error或null | 是 | 比较失败时记录错误 |

评判时隐藏方法名称，a/b为实际展示顺序；保存时记录对应方法。未评价或失败不当作平局。

## 八 通用错误与关联规则

### Error结构

```json
{
  "type": "MODEL_TIMEOUT",
  "message": "模型调用超时"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | string | 是 | 错误类型，如`INVALID_INPUT`、`RETRIEVAL_ERROR`、`MODEL_TIMEOUT`、`GENERATION_ERROR`、`EVALUATION_ERROR` |
| `message` | string | 是 | 可读错误说明，不包含密钥 |

- 文件统一UTF-8；JSONL每行一个对象。示例均为虚构格式，不代表实际结果。
- A的数据按案例编号关联，D的问题按`question_id`关联，回答和评分按四个标识字段关联。
- 上游重复ID、未知问题ID或找不到来源时应报错，不能随意匹配另一条记录。
- 检索无结果：`status=empty`、空上下文、空证据；检索失败不得伪装成空结果或自动切换另一方法。建议生成对应失败回答记录，便于D统计；若检索失败阻止生成，外层`status=error`、答案为空，保留`retrieval.error`，生成耗时为0。
- 生成失败：答案为空、预测类别为`null`、引用为空、`parse_status=not_applicable`，保留错误和耗时。生成成功但字段解析失败仍保留完整答案，外层`status=ok`，`parse_status=error`。
- 三种方法共用任务要求和回答模型配置；参考类别与人工评价不进入生成输入。两种RAG只检索`build_ids`中的资料。
- 本文不约定切块、建图、最大生成树等内部实现，不设置开发、测试或正式阶段标记。
