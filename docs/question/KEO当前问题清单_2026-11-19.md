## 3. 已确认的问题

### 3.1 P1：公共提示词未区分案例题与全局题

位置：`experiments/KEO/core/text_rag/prompt.py` 的 `_TEMPLATE`、`build_prompt()`；`answerer.py` 的 `answer_one()`。

现状：提示词统一要求从 11 类中选择一个类别，并严格输出“类型判定、证据说明、应对措施”三行。`answer_one()` 虽然接收 `question_type`，构造提示词时却没有传递题型。

影响：全局分析问题也会被套入单案分类格式，不能充分回答统计、模式归纳与综合分析问题。后续将类别字段设为 null，不能修复已生成的回答内容。

建议：按 `case_judgment`、`global_analysis` 选择不同模板；三种方法在相同题型下共用同一模板。全局题不要求单一诈骗类别，并保留完整分析正文。

验收：分别选择一道案例题和一道全局题，查看实际发送给模型的提示词及最终回答格式。

### 3.2 P1：全局题的统计要求超出当前局部检索能力

位置：D 的 Demo、全量题库；`core/evaluation/generate_questions.py`；B/C 当前检索链路。

现状：题库包含“总损失最高”“平均损失金额”“主要群体”等问题。B 的 top-k 文本检索和 C 的有限子图检索只能提供部分证据，当前链路没有配套的全库金额、年龄等结构化统计计算。

影响：模型可能将少量检索结果外推为全库统计结论。仅改提示词或跳过检索，不能得到可靠统计。

建议：由团队确定全局题的知识范围与可回答口径。需要精确数值的题增加可追溯的统计模块；仅研究模式归纳时，改用与检索能力匹配的问题与评分标准。不得为回答题目读取评估集统计作为建库知识。

验收：每个数值结论能追溯到统计范围、字段、计算过程；证据不足时明确说明不足。

### 3.3 P1：D 尚未交付与题库配套的参考信息

位置：`output/v1.0/questions/`；配置 `QUESTION_METADATA`、`QUESTION_METADATA_FULL`。

现状：目前有两份题库和接口说明，没有两份 metadata 文件。配置中的路径只是预留，不代表文件已经存在。

影响：依赖真实类别的 Accuracy、Macro-F1，以及读取 metadata 的评分入口无法完整运行。

建议：优先请 D 交付两套格式 1.5 数据，包含 `question_id`、`origin_source_ids`、`gold_category`。已有反推工具只能作为辅助，反推结果需由 D 核对，不能直接宣称为正式金标。

验收：两份题库分别与各自 metadata 对齐；案例题来源属于 eval_ids；参考信息不传给回答模型。Demo 与全量的题号长度不同，不能混用 metadata。

### 3.4 P1：成对评估仍使用占位密钥

位置：`core/evaluation/run_pairwise.py` 配置区。

现状：路径已经改正，但 API 密钥仍是占位字符串，模型与服务地址也由该文件单独定义。

影响：成对评分无法按当前公共配置正常调用，并可能与其他评分入口采用不同配置。

建议：与公共配置统一读取密钥、服务地址和明确的评判模型；不要把真实密钥写入代码。

验收：在本机环境配置下完成一组成对评分，并记录实际 evaluator_id。

### 3.5 P1：分类指标缺少答卷完整性与批次检查

位置：`core/evaluation/metrics.py` 的 `compute()`。

现状：按答卷中实际出现的记录累计分母，没有先构造“预期问题 × 方法”集合，也没有要求单一 run_id、model_id 或拒绝重复记录。

影响：漏掉的题不计入分母，可能使准确率偏高；混入多个批次或重复答卷会重复计数；未知题号因没有金标而被跳过。

建议：评分前按题库、运行批次与方法校验完整性，明确报告缺失、重复、失败、未知题号。类别指标使用事先确定的类别集合和统一缺失处理规则。

验收：故意删除、复制一条答卷或混入另一个 run_id，程序能明确报错或单独报告，不能悄悄输出普通成绩。

### 3.6 P1：成对评估可能混用不同批次或模型的回答

位置：`core/evaluation/run_pairwise.py` 的 `answer_pairs` 分组逻辑。

现状：只按 question_id、method 分组，后读入的同键回答覆盖前面的记录，没有把 run_id、model_id 纳入分组。模型调用或解析失败也没有完整的失败结果记录；A/B 展示顺序没有平衡。

影响：可能比较不同批次或不同模型；失败比较从结果中消失；固定展示顺序可能引入位置偏差。

建议：明确选择同一批次、同一回答模型的答卷，按完整键校验；所有预期比较均保存成功或失败记录；平衡或随机化 A/B 展示顺序并保存映射。

验收：混合两批答卷时不会交叉比较；失败仍有可重试的记录；三种方法每题对应三组成对比较。

### 3.7 P1：B 检索结果的覆盖检查发生在写入之后

位置：`core/text_rag/run_b.py` 最终写文件部分。

现状：`write_jsonl(retrieval_out, final_retrieval)` 先执行，之后才调用 `_guard_shrink()`。

影响：小批量运行指向已有正式文件时，旧检索结果可能已经被覆盖，后续检查无法保护原数据。

建议：所有检查先执行，再写入临时文件并替换正式文件；按运行批次隔离结果目录。

验收：已有较大结果文件时，以较小结果重复运行且不加 force，原文件内容保持不变。

### 3.8 P2：B 文本索引缺少数据与配置指纹

位置：`core/text_rag/build_index.py` 的 `done_cases.json`、集合创建与续建逻辑。

现状：完成标记主要按案例 ID 保存，没有绑定原文内容、数据版本、切块参数、Embedding 服务与模型等完整指纹。

影响：修改原文或切块参数后重跑，已完成案例可能直接跳过；相同目录可能混入旧向量。仅 Embedding 维度相同不能证明索引兼容。

建议：保存数据摘要、切块参数和 Embedding 指纹；不兼容时拒绝续建，使用新目录重建。更新案例时清理已失效的旧文本块。

验收：修改一篇原文、切块窗口或模型后，系统能识别变化，不会继续报告原索引已全部完成。

### 3.9 P2：查询入口会自动创建不存在的文本索引集合

位置：`core/text_rag/retrieve.py` 的 `open_collection()`。

现状：查询使用 `get_or_create_collection()`。

影响：集合名或目录错误、尚未建库时，会生成空集合，容易将部署错误误判为正常无检索结果。

建议：查询只打开已存在且通过完整性检查的集合；不存在、为空或版本不符时返回清楚的配置/索引错误。

验收：给出错误的索引目录或集合名时明确失败，不创建新的空知识库。

### 3.10 P2：单条评分没有直接核对实际检索证据，失败续跑也会被跳过

位置：`core/evaluation/run_eval.py` 的 `work()`、`score_one()` 调用及 resume 的 done 集合。

现状：评判输入主要是问题、真实类别与回答正文，没有把答卷中的实际 retrieval.context、evidence 一并交给评分函数。续跑完成集合包含既有失败记录；题库找不到题号时仅打印并跳过。

影响：无法充分核对引用是否被真实检索证据支持；评分失败后续跑可能仍不重试；错题库可能产生不完整评分。

建议：评估引用忠实度时提供实际证据并检查引用 ID；续跑默认跳过成功项、重试失败项；缺题号应作为完整性问题处理。

验收：加入一条无证据支持的引用和一条评分失败记录，分别能被识别、重试。

### 3.11 P2：汇总报告混合案例题与全局题的评分维度

位置：`core/evaluation/report.py` 五维评分汇总。

现状：汇总统一使用案例题维度，缺少的维度用 0 补齐，标题也固定为 Demo。

影响：全局题维度与案例题不完全一致时，平均分和总分口径失真；正式题库报告名称也容易混淆。

建议：按题型分别统计各自维度，显示理论满分、成功数与失败数；从运行信息生成报告标题，并限定 run_id、model_id。

验收：混合两类题时分别给出正确维度与分母，全局题不因缺少案例专属维度而被补零扣分。

### 3.12 P2：C 的有限查询缺少稳定截取顺序

位置：`core/graph_rag/neo4j_store.py` 的子图事实截取与证据查询，约 1508、1564 行附近。

现状：部分查询使用 LIMIT 控制规模，但截取前没有明确 ORDER BY。

影响：达到规模上限时，同一问题可能取到不同事实或证据，影响上下文与实验复现。该问题不表示查询会取回全图。

建议：在限制规模前定义明确排序，包含确定的唯一 ID 作为并列排序依据；业务相关性排序与规模限制配套设计。

验收：固定数据版本、种子与参数，多次检索返回相同的事实和证据集合。

### 3.13 P2：统一入口没有冻结实际知识库版本

位置：`core/run_experiment.py` 的运行 manifest 与 resume 检查。

现状：已经记录题库、划分名单、提示词摘要及模型配置，但没有完整记录实际文本索引内容版本，以及 Neo4j/图谱向量库的同步版本。

影响：路径、题库不变而知识库内容更新后，旧 run_id 续跑仍可能拼接两版知识库的答案。

建议：记录并校验 B 索引构建指纹、C 图谱与向量同步版本；正式运行冻结知识库，版本变化后改用新 run_id。

验收：中途更新知识库再续跑时，入口能识别变化并拒绝混合结果。

### 3.14 P2：BC 的上下文预算与正式实验参数尚需统一

位置：B 的 top-k 检索参数、C 的 MAX_CONTEXT_CHARS、统一实验入口。

现状：B 主要按检索条数限制，C 还按字符数限制；共用回答模型不等于输入证据预算相同。

影响：回答差异可能来自上下文长短，而非检索方法本身。

建议：明确实验控制条件，记录每题实际上下文长度，优先统一 token 预算；若采用不同预算，应在论文中说明并增加消融对比。

验收：运行清单可查到两方法预算及实际长度，三种方法共用回答模型、温度和输出预算。

## 4. 需要运行确认的事项

以下不是已经证明的故障，不能仅凭输入路径推断正常或异常：

1. **Neo4j 是否仍是旧小样本库**：检查来源覆盖、事实数、是否存在不属于当前 build_ids 的来源。文件整理不会自动导入数据库。
2. **C 向量是否同步完成**：检查图谱和向量状态、版本、待处理任务与节点对应关系；未同步完成不得开放正式查询。
3. **B 索引是否覆盖完整建库集**：不能只看目录存在或 done_cases 数量；应核对案例范围、文本块数量与构建配置。
4. **原文与三元组是否逐项一致**：目前核对的是来源范围及交付校验值，不等于已经对每条三元组做语义正确性审核。
5. **删除更新是否保留共享节点其他来源**：以两个案例共用一个概念为例，删除其中一个来源，检查另一个来源、证据和向量仍可用；最后一个来源删除后的清理也要核验。
6. **大规模导入和查询的资源占用**：记录 60 万级三元组导入耗时、失败恢复、Neo4j 内存与有上限查询的延迟。小样本成功不能直接证明正式规模稳定。
