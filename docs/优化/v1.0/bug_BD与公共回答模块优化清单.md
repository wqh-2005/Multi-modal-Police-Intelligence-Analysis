# B、C、D 与公共回答模块优化清单

整理日期：2026-11-20。

依据：当前代码静态检查，以及 `demo200_full_v1` 的 200 题、600 条答卷结果。

本文只记录问题与建议，不表示这些改动已经实现。三种方法指同一回答模型下的直接回答、文本 RAG 和图谱 RAG。

## 1. 优化目标与原则

目标是让检索增益能被回答模块表达，并由评估模块可靠识别。在此基础上验证图谱 RAG 是否优于其他方法。

- 三种方法使用同一题库、回答模型和对应题型的公共提示词。
- BC 使用同一建库案例范围，参考答案与评估来源信息不进入回答流程。
- 不通过降低 B 基线质量、选择性删题或偏向图谱的评分标准制造优势。
- 已分析的 200 道题作为开发参考；最终测试集应保持独立。
- 保留 v1.0 原始答卷，新实验使用新 run_id，避免覆盖。

## 2. D：评估与参考信息

### D-01｜最高优先级：补齐正式参考信息

相关文件：

- `experiments/KEO/configs/config.py`
- `experiments/KEO/core/ingest_question_metadata.py`
- `experiments/KEO/output/v1.0/questions/`

问题：当前交付的 Demo、全量题库缺少配套正式 metadata。本轮分类分析通过题干匹配 A 评估原文取得参考类别，不能代替 D 对参考信息的正式核对。

建议：D 分别交付两份格式 1.5 文件，包含 `question_id`、`origin_source_ids`、`gold_category`；对边界类别、争议案例进行人工复核。反推工具仅作为辅助。

预期路径：

```text
questions/Demo版/question_metadata.jsonl
questions/全量版/question_metadata_full.jsonl
```

验收：题库与 metadata 逐题对应，无重复或缺失；案例题来源属于 eval_ids；全局题不强行标单一诈骗类别；真实类别不传给回答模型。

### D-02｜最高优先级：分开评价分类、案情依据与历史引用

相关文件：`core/evaluation/run_eval.py`、`metrics.py`。

问题：分类、证据支持程度和防范建议是不同能力。仅看是否出现 E001 不能证明证据正确；直接回答本身没有检索编号，不能因此机械判定其案情分析差。

建议：

1. 分类由程序计算 Accuracy、Macro-F1 与逐类别结果。
2. 三种方法均评价对当前案情的依据提取是否准确。
3. 两种 RAG 另外评价历史资料相关性、引用忠实度及是否混淆当前案件与历史案件。
4. 防范建议的正确性、可执行性和完整性使用统一标准。

验收：没有检索的直接回答仍可获得案情依据分；引用了无关资料的 RAG 不会仅因有编号获得高分；分类指标与主观评分分开呈现。

### D-03｜最高优先级：评分时提供实际检索证据

相关文件：`core/evaluation/run_eval.py` 的 `work()` 与 `score_one()`。

问题：当前评分调用没有将答卷里的实际 retrieval.context、evidence 一并传给评分函数，难以核对引用支持关系。

建议：评分输入包含问题、原始回答、实际证据与引用映射。参考类别只供评判使用。评分端应将待评文本视为数据，不能服从其中夹带的指令。

验收：人为构造不存在的引用、无关引用、支持结论的引用，评分和程序检查能区分三者；每条证据评价可追溯。

### D-04｜最高优先级：答卷完整性与批次校验

相关文件：`core/evaluation/metrics.py`、`run_eval.py`、`run_pairwise.py`。

问题：分类统计主要按已有记录累计；成对比较主要按 question_id、method 分组。缺题、重复和跨批次混入会影响结果。

建议：以 `run_id＋model_id＋question_id＋method` 为完整记录键，先与预期题目和方法集合核对，再评分。明确记录缺失、重复、未知题号与失败项。

验收：删除、复制一条答卷，或混入其他 run_id/model_id 后，程序明确报告问题；不静默缩小分母或覆盖记录。

### D-05｜高优先级：修复评分失败续跑

相关文件：`core/evaluation/run_eval.py`。

问题：当前 resume 的完成集合包含失败记录，可能使失败评分在续跑时被跳过。

建议：默认只跳过成功评分，对可重试失败与未完成项继续处理；记录评判模型和评分规则版本，规则变化时不能混用旧评分。

验收：已有成功、失败、缺失三种记录时，续跑保留成功项并处理后两类，不生成重复记录。

### D-06｜高优先级：成对评分配置与比较设计

相关文件：`core/evaluation/run_pairwise.py`。

问题：仍有占位 API 密钥及独立模型配置；A/B 展示顺序未平衡，调用失败没有完整结果记录。

建议：统一从配置读取密钥与服务地址，明确评判模型；只比较同批次、同回答模型的记录；随机化或平衡 A/B 位置并保存映射；每组比较都保存成功或失败结果。

验收：无需在代码中填写真实密钥；每题三种方法产生三组预期比较；失败可追溯和续跑；不跨批次配对。

### D-07｜高优先级：案例题和全局题分开汇总

相关文件：`core/evaluation/report.py`、`run_eval.py`。

问题：报告统一按案例题维度汇总，缺失维度补零，标题固定为 Demo，可能使全局题得分失真。

建议：按题型分别列维度、满分、有效数和失败数；使用运行信息生成标题；限定报告的 run_id/model_id。

验收：两类题采用各自维度，全局题不因缺案例专属维度被补零扣分；报告注明题库、批次和方法范围。

### D-08｜高优先级：开发集、独立测试集及统计口径

问题：目前 200 道题已用于错误分析，继续据此调参后，其分数不能当作完全独立的测试成绩。题目类别分布也不均衡。

建议：固定开发集；另外保留未参与调参的测试集，检查与建库侧的近重复案例。报告 Accuracy、Macro-F1、类别支持数、失败率和耗时；通过配对统计与置信区间评价差异，不能将一两题差异直接表述为显著提升。

验收：开发与测试来源可追溯；最终测试不参与反复调参；提供完整方法对比与不确定性说明。

## 3. B 维护的公共回答模块

本节同时影响 direct、text_rag、graph_rag，修改时应三种方法共同更新。

### G-01｜最高优先级：改进过度简化的回答要求

相关文件：`core/text_rag/prompt.py`、`answerer.py`。

问题：目前要求三行输出，证据部分主要填写编号，没有充分要求解释事实如何支持结论。图谱检索获得的关系链可能难以体现在答案中。

建议的公共内容结构：

```text
类型判定：……
案情依据：说明当前题目中的关键借口、行为和判断依据。
参考证据：有检索资料时解释其相关性并引用编号；无资料则明确说明。
应对措施：……
```

必须明确：历史案例事实不能写成当前案件已经发生的事实；不能为了提高引用率而强制无依据引用。

验收：三种方法都能提取当前案情依据；RAG 引用能说明对应关系；无检索资料时不编造编号。若调整输出结构，应同步解析逻辑并保留格式 1.4 对外字段。

### G-02｜最高优先级：按 question_type 选择模板

相关文件：`core/text_rag/answerer.py`、`prompt.py`。

问题：`answer_one()` 接收 question_type，但调用 build_prompt() 时没有传入，全局题仍使用单案分类模板。

建议：案例研判与全局分析分开模板；同一题型下三种方法共用任务要求。全局题不强制输出诈骗类别，精确统计只能来自可核验的计算结果。

验收：分别检查两类题实际提示词和解析结果，全局题的 predicted_category 为 null，且回答内容适配分析任务。

### G-03｜高优先级：保留原始引用与非法引用信息

相关文件：`core/text_rag/answerer.py` 的引用解析。

问题：当前解析过滤不在允许集合中的引用，可能掩盖模型生成了错误编号的事实。

建议：保留原始回答，并在内部诊断信息中区分原始引用、有效引用、不存在的引用。不要改变现有有效引用字段的语义；新增信息需要与 D 约定。

验收：模型输出 E999 而证据仅有 E001 时，可报告错误引用，不只是得到空引用列表。

### G-04｜高优先级：错误分类、重试及运行可观测性

相关文件：公共模型客户端、`answerer.py`、`core/run_experiment.py`。

问题：本轮 q078 返回 HTTP 451。服务拒绝、限流、超时、解析失败和检索失败需要分别记录，不能混为普通分类错误。

建议：仅对适合重试的临时失败执行有界重试；保留服务拒绝结果，不通过改写或绕过限制掩盖失败。记录尝试次数、失败耗时及可获得的 token 使用量。不能静默切换模型或降级到直接回答。

验收：失败原因可区分，续跑可控；报告同时显示分类结果与运行失败；重试不会悄悄改变实验条件。

## 4. B：文本 RAG 与索引

### B-01｜最高优先级：统一清理附加类别标签

相关位置：建库前的数据准备流程、`core/text_rag/build_data.py`，以及 C 的对应证据来源。

问题：部分案情原文带有附加类别名称，可能直接提示答案。本轮 B 有 12 道题的检索证据文本命中类别名称字符串，但仍需区分自然表述与人为标签。

建议：BC 采用统一清理规则，对确认属于附加标注的内容处理；保留原件和清理记录。不要删除案情中自然表达的业务含义。数据变化后重建相关索引并记录版本。

验收：抽查命中记录；附加标签不再进入回答上下文，原文证据与来源仍能追溯；两种方法执行相同口径。

### B-02｜最高优先级：建库入口实际核对建库范围

相关文件：`core/text_rag/build_data.py`、`build_index.py`。

问题：建库主流程读取角色切片，主要依赖交付包已经筛好。辅助校验存在不等于每次建库入口都会执行。

建议：正式建库前核对案例 ID 与 build_ids，拒绝重复和评估来源；小样本模式显式允许子集，并记录实际使用范围。

验收：混入 eval 案例或重复案例时拒绝建库；正式模式能识别缺失案例；样本模式明确记录子集。

### B-03｜高优先级：索引数据与配置指纹

相关文件：`core/text_rag/build_index.py`。

问题：done_cases 主要以案例 ID 记录完成，不能充分识别原文、切块参数和 Embedding 配置变化。

建议：记录数据摘要、Embedding 服务/模型、切块参数和构建版本；不兼容时拒绝沿用索引。案例更新时清理失效旧块，防止新旧文本混存。

验收：修改原文或参数后不会仅因 ID 已完成而跳过；运行 manifest 能追溯实际索引版本。

### B-04｜高优先级：查询只打开已建索引

相关文件：`core/text_rag/retrieve.py` 的 open_collection()。

问题：查询使用 get_or_create_collection()，错误路径或集合名可能生成空集合，被当作正常无结果。

建议：查询只打开已存在、版本匹配的索引；缺失、空库或不兼容配置应明确报告。

验收：输入错误索引目录、集合名时返回索引错误，不自动创建空知识库。

### B-05｜高优先级：保护结果文件

相关文件：`core/text_rag/run_b.py`。

问题：检索结果写入发生在覆盖保护检查之前，小批量运行可能先覆盖旧文件。

建议：先完成所有覆盖与完整性检查，再通过临时文件替换；按 run_id 隔离输出。

验收：小结果覆盖大结果且未明确允许时，旧文件内容保持不变。

### B-06｜后续增强：文本块与证据编号准确性

相关文件：`core/text_rag/clause.py`、`build_index.py`。

建议：检查过长整案、过短片段和相邻窗口重复；窗口合并后保留实际包含的语句单元列表或原文范围，不因 chunk_id 形式相似就假定它与 C 的单个 unit_id 内容相同。

验收：每个检索块可以还原到原案情位置；关键上下文不被随意切断；与 C 对照证据时按实际内容和范围核验。

### B-07｜后续增强：减少检索噪声

相关文件：`core/text_rag/retrieve.py`。

问题：本轮相对直接回答，文本 RAG 改对 9 题，也改错 7 题，虚假购物服务类表现退化。

建议：在候选召回后加入去重、单案占比控制及相关性重排，重点检查不同诈骗手法的相近词干扰。统一上下文预算，记录实际长度。

验收：分别统计改对与改错；通过消融验证增强模块的收益，不能只增加 top-k 后宣称改善。

## 5. C：图谱 RAG 检索与上下文

本节依据本轮结果与当前代码，区分已确认的实现限制和待验证的效果原因。保留原有人员身份、共享概念和来源追溯规则，不通过合并不同案例的人员节点解决检索问题。

### C-01｜最高优先级：增加检索过程诊断

相关文件：`core/graph_rag/graph_retriever.py`、`context_builder.py`、`api.py`。

问题：最终答卷能够看到上下文，但不足以直接定位噪声在哪一步进入，以及正确事实在哪一步被丢弃。

建议：在可选诊断输出中记录种子节点与分数、候选事实、入选/淘汰原因、生成森林前后事实、证据排序及预算截断情况。按 run_id/question_id 保存，维持格式 1.3 的既有对外职责，不将调试明细塞入回答上下文。

验收：针对改对、改错各选若干题，能完整还原“问题→种子→候选→筛选→证据→回答”，并定位关键证据是否曾被召回。

### C-02｜高优先级：种子检索缺少诈骗行为语义

相关文件：`core/graph_rag/node_index.py` 的 `_build_record()`、`graph_retriever.py`；新增索引时配套数据模型与配置。

问题：目前节点向量描述主要包含名称、类型、角色、图谱分类和展示名称。整篇案情匹配简单实体描述，容易命中“客服、平台、微信”等泛化概念，难以区分诈骗借口与行为组合。

建议：保留实体/别名检索，研究增加事实或小型关系链的语义召回，再通过 triple_id/source_id 回到 Neo4j 获取关联证据。先做离线候选对照，再决定是否全量建立新索引；不将评估类别或题目参考答案写入描述。

验收：以“注销学生账户→申请贷款→向指定账户转账”等查询，检查是否优先召回对应行为链，而不是仅召回含客服的案件；与当前节点召回做消融对比。

说明：新增事实向量需要独立的索引身份、版本与增量同步设计，不能直接混写进现有节点向量集合。更新描述版本也需要按既有机制同步或重建。

### C-03｜最高优先级：邻域扩展在相关性筛选前截断

相关文件：`core/graph_rag/neo4j_store.py` 的 `get_subgraph()`、`graph_retriever.py`。

问题：当前部分邻居查询在排序前执行 `WITH f LIMIT $limit`。热门共享概念连接很多案例时，有价值的事实可能尚未进入后续筛选就被截断；没有稳定顺序也影响复现。

建议：在有限候选范围内对事实、案件或关系链重排，再补齐入选案件必要关联事实。增加稳定的 ID 并列排序，同时考虑问题相关性；限制单个热门概念和单个案例对预算的占用。不能为了重排先取回全图。

验收：固定版本与参数时结果可复现；客服、微信等高连接度节点不会占满候选预算；抽查关键手法证据的召回与入选情况。

### C-04｜最高优先级：最大生成森林权重未充分反映问题相关性

相关文件：`core/graph_rag/context_builder.py` 的 `_select_edges()`。

问题：当前以“头节点 ID＋关系＋尾节点 ID”的来源支持数作为边权。人员按案例独立，许多涉及人员的事实支持数天然只有 1，该权重可能缺乏判别力。种子相似度主要决定选树后的展示顺序，无法恢复此前丢弃的事实。

建议：统计实际边权分布，比较当前方案与问题相关性选边方案。若保留生成森林，将相关性纳入选边前的权重，并验证是否需要补回高相关事实。

验收：记录边权分布、保留事实与丢弃事实；用相同候选、相同预算比较两种筛选策略，不能仅凭替换权重就宣称更优。

### C-05｜高优先级：树结构可能丢失关键业务关系

相关文件：`core/graph_rag/context_builder.py`。

问题：生成森林倾向保留连通骨架，但分类所需的可能是多条关系组合。当前使用无向 MultiGraph 做筛选，平行关系与构成环的事实可能被舍弃；不能将树选出的连通路径当作新增业务事实。

建议：比较“生成森林”与“相关事实＋必要关系链”方案；输出时保留原关系方向、factuality 和原始 triple_id，允许补回关键关系。先评估，再决定是否替换论文方法中的生成树环节。

验收：同一人员涉及的冒充、要求下载、要求转账等关键事实不会仅因树约束而无解释地消失；任何关系都有原始证据，不跨案例拼接不同人员身份。

### C-06｜最高优先级：上下文冗长，证据利用不足

相关文件：`core/graph_rag/context_builder.py`；配合 B 的 `prompt.py`、`answerer.py`。

现象：本轮平均上下文约 7,344 字符、15.89 条证据，约为 B 上下文的 5 倍，但仅 18/200 条回答明确引用证据。该结果证明显式引用不足，不能单凭没有编号就断言模型完全没参考资料。

建议：按案件组织“关键关系链＋原文证据”，移除给回答模型展示的冗长节点 ID，合并重复事实与重叠证据；按相关性分配预算，限制单案占比。保留原文、方向、事实状态和来源映射。共同修订公共提示词，让回答说明历史资料支持什么，允许证据不足时不引用。

验收：固定上下文预算后比较结果；压缩后仍能追溯每条事实与证据；不仅统计引用比例，还抽查引用是否相关、是否支持结论。不能通过强制引用虚增分数。

### C-07｜高优先级：专项排查虚假征信类退化

相关文件：`graph_retriever.py`、`context_builder.py`，以及相应诊断结果。

现象：本轮虚假征信类，直接回答正确 15/20，文本 RAG 16/20，图谱 RAG 11/20。

待验证假设：检索过度关注冒充机构、客服身份，弱化了注销账户、清空贷款额度、更改身份等具体行为，导致相邻类别混淆。这不是已经证实的唯一原因。

建议：逐题复盘该类错误，分别核对种子、候选、入选证据和回答；建立同类手法与相邻类别的对照案例。不要增加仅匹配这 20 道题的硬编码规则。

验收：改善该类表现时，同时检查客服类、贷款类等其他类别是否退化；最终在未参与调参的题目上复验。

### C-08｜高优先级：冻结图谱与向量库的实际版本

相关文件：`core/graph_rag/neo4j_store.py`、`node_index.py`、`core/run_experiment.py`。

现状：C 已有 ready 状态、Embedding 指纹与集合身份校验，应保留这些保护。统一运行清单仍需进一步绑定实际知识库版本，避免同一路径下内容变化后续跑混用两版数据。

建议：实验开始时记录图谱版本和同步目标身份，在运行期间及恢复时校验；知识库更新后使用新 run_id。保留增量更新、失败恢复和共享节点多来源追溯。

验收：中途更新知识库后恢复旧运行，能识别版本变化；删除一个案例不影响其他案例共用概念的事实、证据和向量；失败同步不能开放查询。

### C-09｜后续研究：任务覆盖与图谱贡献验证

相关位置：与 D 协作的题库、评分标准和消融实验。

问题：单案分类的题干本身已经包含大量信息，直接回答达到 79.5%，图谱提升空间有限。不能仅靠增加证据量证明图结构有效。

建议：在保留分类任务的同时，增加同身份不同手法对比、跨案例关系组合、可追溯模式归纳等任务，三种方法回答相同问题并分任务报告。精确金额或数量统计应增加结构化计算，不能从局部子图猜全库结论。

验收：题目由预先确定的业务需求与规则产生，不根据 C 能答对哪些题选择；完成“无图扩展、无关系链筛选”等消融，证明收益来自图谱设计而不是更多上下文或不同模型。

### C 的建议实施顺序

1. 增加可选诊断输出，定位改错案例的关键环节。
2. 改进有限候选排序、生成森林/关系链筛选和上下文压缩。
3. 用同一开发集、同一预算做逐项消融，检查分类、证据质量与耗时。
4. 前述改动仍无法改善召回时，再投入事实或关系链索引。
5. 冻结知识库与参数，在独立测试集上验证。

前两阶段主要涉及查询和上下文流程，通常不需要重新抽取三元组，也不必立即重算全部节点向量。
